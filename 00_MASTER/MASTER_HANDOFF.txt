7. IMPORTANT PAST BLOCKERS AND WHAT WAS FIXED
======================================================================

A. Initial Scudo / allocator crash
----------------------------------
Earlier the engine died around Android SDL storage path ownership.
A likely/observed startup blocker involved freeing paths returned by:
- SDL_GetAndroidExternalStoragePath()
- SDL_GetAndroidInternalStoragePath()

A patch removed the problematic SDL_free calls.
After that the engine progressed deep into INI loading and renderer startup.
Do not casually reintroduce those frees.

Also important:
Tarek's engineering notes state:
RTS_GAMEMEMORY_ENABLE=OFF
is required for the Android build because the original game DMA/custom allocator conflicts with libc++ / external allocations.

However the current cache had:
RTS_GAMEMEMORY_ENABLE=ON

This is a FUTURE stability risk, not the current renderer blocker.
If Scudo/allocator crashes return after rendering starts, rebuild engine with RTS_GAMEMEMORY_ENABLE=OFF according to Tarek's Android engineering notes.

B. First renderer blocker: VK_EXT_robustness2
---------------------------------------------
The packaged Tarek DXVK 2.6.0 reached the Mali GPU but failed with:
Required Vulkan extension VK_EXT_robustness2 not supported
DxvkAdapter: Failed to create device

That proved the official packaged DXVK did not support this Mali driver sufficiently.

Therefore we started building a Mali-oriented/fbraz3 DXVK.

C. DXVK build tooling blockers that are ALREADY SOLVED
------------------------------------------------------
Solved:
- glslang
- SPIRV-Headers
- Vulkan-Headers
- recursive submodules
- dxbc-spirv
- libdisplay-info
- pkg-config shim for SDL3
- Windows `touch` program for Meson

DXVK 2.7.1 now builds successfully with about 370 Ninja steps.

Confirmed successful output:
...\build-android-real\src\d3d8\libdxvk_d3d8.so
...\build-android-real\src\d3d9\libdxvk_d3d9.so

D. SDL3 WSI loader
------------------
New DXVK 2.7.1 originally failed:
SDL3 WSI: Failed to load SDL3 DLL.

Audit proved source uses:
LoadLibraryA("libSDL3.so")

libSDL3.so's ELF SONAME is also:
libSDL3.so

We added an Android-specific direct POSIX loader path in:
src/wsi/sdl3/wsi_platform_sdl3.cpp

The working runtime log later proved:
ZH_ANDROID_SDL3_DLOPEN_OK

This is IMPORTANT:
The Android SDL3 direct-dlopen patch is proven working and should be retained while rebuilding DXVK.

The intended Android-only concept is:
- dlopen("libSDL3.so", RTLD_NOW | RTLD_LOCAL)
- cast the handle into the type expected by the existing DXVK WSI code
- retain GetProcAddress function loading afterward
- log failure/success

E. Native library packaging / bad ELF magic
--------------------------------------------
At one point Android logcat showed:
libdxvk_d3d9.so has bad ELF magic: 504b0304

504B0304 = ZIP signature, not ELF.

This was treated as an APK/native-library packaging issue.

Repair verified:
- staged d3d8/d3d9/SDL3 begin with ELF magic 7F454C46
- JNI packaging uses non-legacy packaging
- libraries inside APK are stored/uncompressed and aligned
- after repair the log explicitly said:
BAD ELF / ZIP-MAGIC BLOCKER: GONE

Do NOT regress this.

Important Gradle packaging setting:
useLegacyPackaging false

When packaging:
- verify libdxvk_d3d8.so
- libdxvk_d3d9.so
- libSDL3.so
inside APK are real ELF files (magic 7F454C46)
- verify they are ZIP_STORED/uncompressed
- verify zipalign/page alignment, preferably 16K-aware for modern Android.

12. NORMAL RTS TOUCH CONTROL — PROJECT CONSTITUTION
======================================================================

The user approved a premium touch-control design with these hard rules:

A. PRESERVE ZERO HOUR
---------------------
- Original Zero Hour Command Bar and Minimap are protected.
- Do not permanently redesign the original UI.
- Added touch UI must keep Zero Hour visual DNA.
- New buttons/elements must look modern and impressive but still unmistakably Zero Hour.
- Extra controls should be transient/contextual, not permanent clutter.
- Do not change game rules just to make touch easier.

B. TOUCH SHOULD REDUCE APM
--------------------------
The goal is not merely emulate a mouse.
The goal is to make touch natural, fast, low-APM, and potentially better than mouse/keyboard for common mobile interactions.

C. INPUT ARCHITECTURE
---------------------
Approved conceptual pipeline:

Raw Touch
   ->
Gesture Features
   ->
Context
   ->
Intent
   ->
Safety
   ->
SAGE Command

Meaning:
- Raw touch is not allowed to directly mutate game state.
- Gestures are interpreted.
- Current unit/target/UI context is considered.
- The system resolves a gameplay intent.
- Safety checks validate it.
- Only then is a real SAGE command issued.

This layer should be:
- deterministic
- replay-safe
- multiplayer/network-safe
- fail-closed
- based on real SAGE commands, not fake local transforms

D. APPROVED PREMIUM TOUCH FEATURES
----------------------------------

1) Precision Target Lens
Approved.
Purpose:
- Improve precise targeting on a small touchscreen.
- Used when exact target selection is difficult.
- It is an assistive transient overlay, not a permanent UI replacement.
- It must preserve the actual underlying SAGE target/command rules.

2) Direct Formation Preview
Approved.
Purpose:
- Before committing a formation/movement gesture, show a temporary visual preview of the intended formation/destination.
- The preview disappears after commit/cancel.
- It should not create a fake separate formation system; final order must become real SAGE commands.

3) Quick Orders Fan
Approved as a transient quick-order UI.
Rules:
- Appears temporarily only when context calls for it.
- Visual design must look like modernized Zero Hour-native controls.
- Must not permanently alter the Command Bar.
- Final action issues real existing game commands.

4) Drag-to-Target
Approved.
Concept:
- Original Zero Hour command buttons remain.
- A touch user can drag from an original/context command toward the intended world target rather than requiring awkward multi-step mouse emulation.
- The touch layer resolves target context then issues the real SAGE order.

5) Build Placement Assistant
Approved.
Core interaction:
- Tap original build action = normal build action.
- Hold = enter a richer placement/rotation interaction.
- This assists touchscreen placement while preserving real building placement rules.
- The overlay/assistant is transient.

6) Touch Intent Preview
Approved.
Purpose:
- Before a potentially ambiguous touch command commits, temporarily show what the system thinks the user intends.
- Helps prevent wrong move/attack/target/build actions.
- Must be fast and non-obtrusive.

7) Smart Haptic Language
Approved.
Use vibration/haptics as a compact feedback language.
Examples of categories that may be distinguished:
- selection/lock
- valid command
- invalid command
- target acquisition
- destructive/high-risk action
Keep it subtle; it is feedback, not gameplay logic.

8) Waypoint Path Echo
Approved as part of the touch constitution.
Known rule:
- It is a transient Zero Hour-styled feedback element.
- It must preserve original waypoint/command logic and determinism.
Detailed trigger/visual specification was not fully recoverable from prior chat context, so do not invent irreversible behavior without checking with the user if implementation reaches this feature.

9) Clutch Intent Projection
Approved as part of the touch constitution.
Known rule:
- It is a transient intent/feedback element under the same Zero Hour-native design rules.
- It must not alter game rules.
Detailed trigger/visual specification was not fully recoverable from prior chat context, so preserve the concept/name and avoid silently redefining it.

10) Destructive-command protection
Part of the approved constitution.
The touch-intent/safety layer should protect against accidental high-impact/destructive commands.
It must fail closed on ambiguity rather than issuing a dangerous accidental order.

E. UI RULE
----------
Any added touch button:
- Zero Hour visual identity
- premium/modern execution
- appears only when needed

- no permanent Minecraft-like mobile button wall
