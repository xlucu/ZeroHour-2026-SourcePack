# 2026-08 Development Diary

## 2026-08-11 — Tree-buffer null-deref fix (#8), v0.3 Android build

Triaged the open issues on the Android fork (`tarek369/GeneralsZH-Android`)
and shipped a new alpha build containing one concrete engine fix plus an
allocator mitigation that v0.2 had been missing.

### Issue triage
- **#8 — `W3DTreeBuffer::unitMoved()` SIGSEGV (fault 0x20)**: fixable, fixed.
  Crash fires when a garrisoned unit dies and `OpenContain::redeployOccupants()`
  repositions it; the transform-change callback chain reaches `unitMoved`, which
  dereferences a null `m_data`.
- **#4 / #9 — Scudo allocator crashes (Exynos 2400, Mali-G610)**: re-reported
  against v0.2. Root cause was already addressed in code after v0.2 shipped —
  the symbol-hiding version script (`467d129cc`, committed 09:50 UTC Jul 14)
  landed ~55 minutes *after* the v0.2 release (08:55 UTC). v0.2 therefore still
  exported the engine's `operator new`/`delete`, so DXVK/libc++/SDL3 allocations
  were routed through the pool's `operator delete` and the mincore-based probe
  misclassified them. v0.3 is built from HEAD, which carries the fix.
- **#6 — crash after Solo Play (Z Flip 5, regression vs v0.1)**: plausibly the
  same allocator path; likely improved by v0.3, not confirmable without the
  device.
- **#7 — black-screen crash (Poco X3 Pro, Adreno 640)**: GPU is below the stated
  Adreno 7xx+ minimum; needs logs, likely hardware.
- **#5 — enemy AI not working**: upstream gameplay-logic issue, not
  Android-specific. Out of scope for this build.
- **#3 — high RAM usage**: architectural (legacy pool design), already answered.

### The fix (#8) — root cause
`W3DTreeBuffer::unitMoved()` walked the area partition and, for each candidate
tree, read `m_treeTypes[ m_trees[treeNdx].treeType ].m_data` and dereferenced
it. The only guard was `treeType < 0` (the `DELETED_TREE_TYPE = -2` sentinel).
There was **no upper-bound check** against `m_numTreeTypes` and **no null check**
on `m_data`. `m_treeTypes` is a fixed `TTreeType[64]` array of which only
`[0, m_numTreeTypes)` are initialized; slots at and beyond that index carry a
null `m_data`. The fault address `0x20` matches `W3DTreeDrawModuleData::
m_framesToMoveOutward` exactly (vtable 8 + NameKeyType 4 + pad 4 + AsciiString
8 + AsciiString 8 = 0x20). The redeploy motion is merely the trigger that
sweeps an infantry unit over a stale tree-partition cell mid-frame.

The load path already knew this could happen — it guards with
`treeType != DELETED_TREE_TYPE && treeType < m_numTreeTypes` before indexing.
`unitMoved` lacked the equivalent guard.

### Changes (`Core/GameEngineDevice/Source/W3DDevice/GameClient/W3DTreeBuffer.cpp`)
- `unitMoved()`: bounds-check `treeType < m_numTreeTypes`, null-check `m_data`,
  cache the validated pointer, and deref through it for both the topple and
  push-aside branches.
- `pushAsideTree()`: same bounds + null guard before the
  `m_data->m_framesToMoveOutward` deref (called from `unitMoved`, same hazard).
- `updateTreePosition()`: bounds-check `treeType` before indexing `m_treeTypes`
  for `m_bounds` (deleted/out-of-range reads uninitialized data).

### Build
Incremental rebuild of `libmain.so` (android-vulkan preset). All heavy deps
(DXVK, SDL3, OpenAL, freetype, glm, gamespy, FFmpeg) were already built and
staged in `jniLibs/arm64-v8a/`, so only the engine relinked. Packaged via
`scripts/build/android/package-android-zh.sh` and released as **v0.3-android**
(leaving v0.1-android and v0.2-android intact).

### Honest status
The #8 fix is high-confidence: the fault address is an exact match to the
unguarded deref, and the guard mirrors an existing one elsewhere in the same
file. The Scudo situation (#4/#9) is *expected* to improve because v0.3 carries
the symbol-hiding that v0.2 lacked, but this can only be confirmed by reporters
on the affected Exynos/Mali devices — no deeper allocator change was made, by
choice, since such a change could not be validated here and would risk
regressing devices that currently work.
